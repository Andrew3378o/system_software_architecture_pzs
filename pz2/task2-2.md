## Завдання 2.2
Розгляньте сегменти у виконуваному файлі.
1. Скомпілюйте програму hello world, запустіть ls -l для
виконуваного файлу, щоб отримати його загальний розмір, і
запустіть size, щоб отримати розміри сегментів всередині нього.
2. Додайте оголошення глобального масиву із 1000 int,
перекомпілюйте й повторіть вимірювання. Зверніть увагу на
відмінності.
3. Тепер додайте початкове значення в оголошення масиву
(пам’ятайте, що C не змушує вас вказувати значення для кожного
елемента масиву в ініціалізаторі). Це перемістить масив із сегмента BSS у сегмент даних. Повторіть вимірювання. Зверніть увагу на
різницю.
4. Тепер додайте оголошення великого масиву в локальну функцію.
Оголосіть другий великий локальний масив з ініціалізатором.
Повторіть вимірювання. Дані розташовуються всередині функцій,
залишаючись у виконуваному файлі? Яка різниця, якщо масив
ініціалізований чи ні?
5. Які зміни відбуваються з розмірами файлів і сегментів, якщо ви
компілюєте для налагодження? Для максимальної оптимізації?

Проаналізуйте результати, щоб переконатися, що:
- сегмент даних зберігається у виконуваному файлі;
- сегмент BSS не зберігається у виконуваному файлі (за винятком
примітки щодо його вимог до розміру часу виконання);
- текстовий сегмент більшою мірою піддається перевіркам
оптимізації;
- на розмір файлу a.out впливає компіляція для налагодження, але не
сегменти.

## Технічна реалізація
Для виконання завдання було розроблено програму-автоматизатор на мові C (```task2-2.c```). Замість ручної компіляції, програма використовує функцію system() для автоматичної збірки чотирьох тестових файлів із різними комбінаціями прапорців компілятора GCC (```-O2```, ```-O3```, ```-g``` та без них). Кожен тестовий файл містить масив із 1000 елементів типу int (загальний розмір 4000 байтів), але з різними характеристиками:

```task2-2a.c```: Глобальний неініціалізований масив.

```task2-2b.c```: Глобальний ініціалізований масив.

```task2-2c.c```: Локальний неініціалізований масив.

```task2-2d.c```: Локальний ініціалізований масив.

Після компіляції автоматизатор викликає утиліту ```size``` для аналізу сегментів пам'яті (.text, .data, .bss) та команду ```ls -l``` для визначення фізичного розміру виконуваного файлу на диску.
## Використання
Щоб скомпілювати та запустити головну програму-аналізатор, необхідно виконати наступні команди:
```
gcc task2-2.c -o task2-2
./task2-2
```
Примітка: для коректної роботи файли ```task2-2a.c```, ```task2-2b.c```, ```task2-2c.c```,```task2-2d.c``` повинні знаходитися в тій самій директорії.

## Аналіз результатів
- Глобальні неініціалізовані змінні ```task2-2a```: сегмент .bss збільшується пропорційно розміру масиву (~4000 байтів). Ці дані не зберігаються у бінарному файлі, а лише вказують ОС виділити та занулити пам'ять при запуску.

- Глобальні ініціалізовані змінні ```task2-2b```: сегмент .data різко зростає. Значення зберігаються безпосередньо у виконуваному файлі, що може збільшити його фізичний розмір.

- Локальні змінні ```task2-2c```, ```task2-2d```: сегменти .data та .bss залишаються мінімальними незалежно від ініціалізації. Пам'ять під них виділяється динамічно на стеку (Stack) під час виконання функції. При ініціалізації локальних змінних може незначно зрости сегмент .text, оскільки компілятор генерує інструкції для їх заповнення.

- Вплив прапорця налагодження (-g): pозміри .text, .data та .bss не змінюються порівняно зі стандартною компіляцією. У пам'ять завантажується та сама логіка. Щодо фізичної пам'яті, то файл суттєво збільшується. Це пов'язано з додаванням DWARF-метаданих (таблиці символів, номери рядків) для відлагоджувачів (наприклад, GDB). Ці дані зберігаються на диску, але не впливають на виконання програми.

- Вплив прапорців оптимізації (-O2, -O3) на сегмент коду (.text). При -O2 зазвичай зменшується через видалення невикористовуваного коду. При -O3 може частково збільшитися через агресивне вбудовування функцій (inlining) та розгортання циклів заради швидкості. Сегменти даних (.data / .bss) можуть суттєво зменшитися або зникнути. Оптимізатор визначає, що масиви в тестових файлах не використовуються для реальних обчислень (dead code), і взагалі не виділяє під них пам'ять. Фізичний розмір стає мінімальним, оскільки виконуваний файл містить лише найефективніший набір інструкцій.
