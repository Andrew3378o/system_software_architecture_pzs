## Завдання 3.2
У Docker-контейнері встановіть утиліту `perf`(1). Поекспериментуйте з досягненням процесом встановленого ліміту.

Перш ніж почати експерименти з цією утилітою неоюхідно переконатись, що контейнер запущений з обмеженнями, виконавши команду `sudo docker run --privileged --cpus=".2" -it task3-2`. Вона вказує планувальнику процесів, що цьому контейнеру дозволено працювати лише 200 мс процесорного часу на кожну 1 секунду реального часу.

## Експеримент №1
```
perf stat -e task-clock,cycles,instructions,cpu-clock stress-ng --cpu 1 --timeout 10s
``` 
Виконаємо цю команду, з допомогою якої можна простежити `task-clock` - фактичний процесорний час затрачений на виконання задачі, `cycles` - кількість тактів процесора, витрачених на задачу, `instructions` - кількість операцій, яку встиг виконати процесор, `cpu-clock` - системний час, який іде паралельно з роботою процесора. `stress-ng` - назва утиліти-генератора стрес-тестів для linux. `--cpu 1` - створює один потік, який намагається завантажити одне ядро процесора на 100%. `--timeout 10s` - встановлення тривалості тесту на 10 секунд. Після чого можна побачити вивід схожий на наступний:
```
stress-ng: info:  [31] setting to a 10 second run per stressor
stress-ng: info:  [31] dispatching hogs: 1 cpu
stress-ng: info:  [31] successful run completed in 10.01s

 Performance counter stats for 'stress-ng --cpu 1 --timeout 10s':

           2031.38 msec task-clock                #    0.201 CPUs utilized  
        6164519886      cycles                    #    3.034 GHz            
       10615938128      instructions              #    1.72  insn per cycle 
           2031.79 msec cpu-clock                 #    0.201 CPUs utilized  

      10.091902009 seconds time elapsed

       1.998245000 seconds user
       0.033190000 seconds sys

```

З виводу можна побачити, що після обмеження, було використано `2031.38 msec` процесорного часу на тестування контейнера, тобто приблизно 2 секунди з 10 секунд реальної роботи процесора, як і було вказано у обмеженні на початку.

## Експеримент №2
`perf record -g stress-ng --cpu 1 --timeout 5s` (1)

`perf report` (2)

В теорії після виконання команди (1) буде запущено запис кожної дії процесора, при чому `-g` вказує на запис також ланцюжка викликів, протягом 5 секунд тестування за допомогою тої самої утиліти. Команда (2) відкриває інтерфейс для перегляду відповідного запису. Після їх виконання можна побачити наступний консольний вивід:
```

  Children      Self  Command    Shared Object         Symbol
+   24.56%     0.00%  stress-ng  [unknown]             [.] 0x00000000000000♦
+   24.55%     0.00%  stress-ng  [unknown]             [.] 0x000070e1151fe2▒
+    9.85%     0.00%  stress-ng  [unknown]             [.] 0xc899a9ccca9f10▒
+    9.01%     0.00%  stress-ng  [unknown]             [.] 0x0000000000003f▒
+    6.74%     0.00%  stress-ng  [unknown]             [.] 0xc899007570632d▒
+    3.81%     3.81%  stress-ng  stress-ng             [.] 0x00000000000593▒
+    3.81%     0.00%  stress-ng  stress-ng             [.] 0x00005914289493▒
```
Аналіз результатів `perf report` показав, що основне навантаження (близько 50% сумарно в перших двох гілках) зосереджено в операціях користувацького простору. Невелика кількість зібраних зразків (3K семплів за 5 секунд) свідчить про інтенсивну роботу планувальника, який примусово обмежував час виконання процесу згідно з лімітом `--cpus=".2"`. Наявність великої кількості адрес `[unknown]` пояснюється динамічним завантаженням бібліотек у середовищі контейнера та відсутністю налагоджувальних символів для пакетів `stress-ng` у базовому образі Ubuntu.

## Експеримент №3
```
perf stat -e context-switches,cpu-migrations,page-faults stress-ng --cpu 1 --timeout 10s
```
За допомогою цієї команди можна прослідкувати `content-switches` - кількість перемикань контексту, `cpu-migrations` - кількість міграцій між ядрами процесора, `page-faults` - кількість звернень до пам'яті, які потребували втручання ядра. При виконанні цієї команди можна спостерігати наступний вивід:
```
stress-ng: info:  [41] setting to a 10 second run per stressor
stress-ng: info:  [41] dispatching hogs: 1 cpu
stress-ng: info:  [41] successful run completed in 10.03s

 Performance counter stats for 'stress-ng --cpu 1 --timeout 10s':

               112      context-switches                                    
                 2      cpu-migrations                                      
              1457      page-faults                                         

      10.042083990 seconds time elapsed

       1.999713000 seconds user
       0.014131000 seconds sys
```
Проаналізувавши вивід, можна сказати, що для чисто обчислювальної задачі цифра 112 є відносно невеликою. Це свідчить про те, що планувальник виділяє процесу достатньо великі "шматки" часу перед тим, як призупинити його. Процес не перемикається хаотично, а працює стабільними циклами. Кількість перестрибувань між ядрами процесора дорівнює 2, що свідчить про те, що процесор намагався утримувати процес на одному і тому ж ядрі доволі велику кількість часу. Оскільки `stress-ng` спочатку ініціалізує свої структури даних, більшість цих помилок сторінок сталися під час запуску програми. Для чистого CPU-тесту ця цифра є стабільною і не зростає під час виконання самих обчислень.

## Висновок
Загалом, експерименти продемонстрували, що Docker-ліміти не уповільнюють тактову частоту процесора, а обмежують квоту часу (timeslice) процесу. Утиліта `perf` дозволяє наочно побачити цей «ефект паузи», фіксуючи меншу кількість семплів та пропорційне зменшення task-clock.
