# Завдання 9.1
Напишіть програму, яка читає файл `/etc/passwd` за допомогою команди `getent passwd`, щоб дізнатись, які облікові записи визначені на вашому комп’ютері. Програма повинна визначити, чи є серед них звичайні користувачі (ідентифікатори UID повинні бути більші за 500 або 1000, залежно від вашого дистрибутива), окрім вас.

## Теорія та технічна реалізація 
Системний файл `/etc/passwd` містить базову інформацію про облікові записи користувачів. Проте кращою практикою є використання команди `getent passwd`, оскільки вона враховує не лише локальних користувачів, а й мережеві каталоги (наприклад, LDAP). Для виклику команди та зчитування її результатів використано функцію `popen()`, яка створює канал (pipe) між нашою програмою та виводом системної команди. Далі потік читається по рядках (`fgets`), а функція `strtok()` розбиває рядок за роздільником `:` для вилучення імені користувача та його UID. Системний виклик `getuid()` використовується для отримання UID поточного користувача, щоб виключити його зі списку.

## Теорія та технічна реалізація 
Файл `/etc/shadow` містить зашифровані хеші паролів користувачів. З міркувань безпеки він доступний для читання лише користувачу `root` (права `600` або `000`). Звичайний користувач не може його прочитати безпосередньо. Програма робить два кроки за допомогою функції `system()`. Спочатку виконується спроба читання без привілеїв (`head -n 2 /etc/shadow`), що генерує помилку доступу. Потім команда викликається через утиліту `sudo` (`sudo head -n 2 /etc/shadow`), яка дозволяє тимчасово підвищити привілеї користувача до адміністративних (за умови наявності відповідних прав у файлі `/etc/sudoers`).

# Завдання 9.3
Напишіть програму, яка від імені root копіює файл, який вона перед цим створила від імені звичайного користувача. Потім вона повинна помістити копію у домашній каталог звичайного користувача. Далі, використовуючи звичайний обліковий запис, програма намагається змінити файл і зберегти зміни. Після цього програма намагається видалити цей файл. Що відбудеться?

## Теорія та технічна реалізація 
Права доступу в Linux працюють по-різному для читання/запису файлів і для їх видалення. Щоб змінити файл, користувач повинен мати права запису (`w`) на сам файл. Щоб видалити файл, користувач повинен мати права запису (`w`) на каталог, у якому цей файл знаходиться. Програма створює тимчасовий файл, потім викликає `sudo cp`, `sudo chown root:root` та `sudo chmod 644`. Таким чином файл належить root і не має прав на запис для інших. Спроба дозапису через `system()` завершується відмовою. Для видалення викликається системна POSIX-функція `unlink()`. Оскільки файл знаходиться у поточному/домашньому каталозі користувача, видалення успішно виконується.

# Завдання 9.5
Напишіть програму, яка створює тимчасовий файл, а потім від імені суперкористувача змінює тип володіння та права доступу. Програма повинна визначити, в яких випадках вона може виконувати читання та запис.

## Теорія та технічна реалізація 
Права доступу в Linux (chmod) визначаються масками. Наприклад:
* `600` — читання та запис тільки для власника (rw-------).
* `644` — читання/запис для власника, тільки читання для решти (rw-r--r--).
* `666` — читання та запис дозволені для всіх (rw-rw-rw-).

Створення безпечного тимчасового файлу реалізовано через функцію `mkstemp()`. Для перевірки прав доступу застосовується POSIX системний виклик `access(filepath, R_OK | W_OK)`. Це найкращий спосіб перевірити, чи має процес реальні права на читання/запис файлу на рівні ядра системи без спроби його фізичного відкриття.

## Теорія та технічна реалізація 
* Каталог `~` (home): повний доступ для користувача.
* Каталог `/usr/bin`: системні бінарні файли. Запис заборонений для всіх, крім root.
* Каталог `/etc`: конфігураційні файли. Запис заборонений.

Щоб виконати скрипт у Linux, файл повинен мати прапорець `x` (execute). Якщо його немає, прямий запуск `./script.sh` завершиться відмовою. У цьому випадку запускається `bash`, який читає файл як текст і виконує його вміст. Використовується `system()` для тестування створення файлів (`touch /usr/bin/test`) та прямого запуску скрипта без прав на виконання, після чого демонструється успішний обхід через виклик інтерпретатора.

## Завдання 9.14 (індивідуальне)
Змоделюйте, як `cron` виконує команду з правами іншого користувача. Коли це не спрацює?

### Теорія та технічна реалізація 
Планувальник завдань `cron` у UNIX/Linux працює у "стерильному", дуже обмеженому оточенні (середовищі). На відміну від звичайної термінальної сесії користувача, `cron` не завантажує файли ініціалізації оболонки (на кшталт `.bashrc` або `.profile`). 
Найбільш критичною відмінністю є змінна `PATH`. У `cron` вона зазвичай звужена до базових `/usr/bin:/bin`. Це означає, що програми, встановлені в домашні каталоги (наприклад, `~/.cargo/bin` або `~/.local/bin`), не будуть знайдені за назвою. Коли cron може не спрацювати?
1. Виклик команди за назвою, а не за абсолютним шляхом, якщо команда не лежить у `/usr/bin` або `/bin`.
2. Недоступність користувацьких змінних оточення (змінних бази даних, тощо).
3. Обмеження прав доступу (скрипт або його ресурси недоступні користувачу, від імені якого `cron` виконує завдання).
4. Обліковий запис заблоковано в `PAM` (встановлено `/usr/sbin/nologin`).
Скрипт створює тестовий Bash-файл та моделює середовище `cron` за допомогою утиліти `env -i`. Ця утиліта повністю очищає змінні оточення поточного процесу. Ми передаємо лише мінімальний `PATH="/usr/bin:/bin"`. Програма порівнює виконання тестового скрипта у звичайному середовищі та в ізольованому.
